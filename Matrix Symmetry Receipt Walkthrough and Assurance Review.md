# Matrix Symmetry Receipt Walkthrough and Assurance Review

## Walkthrough: one real check

The input is a two-by-two matrix:

```text
A = [[1, 2],
     [2, 4]]
```

The requested question is simple: **does the matrix equal its transpose?** For a two-by-two matrix, that means the two off-diagonal entries must match: `A[0,1] = A[1,0]`.

```python
from sov_evidence_geometry_core import check_symmetric_matrix
receipt = check_symmetric_matrix([[1, 2], [2, 4]])
```

| Receipt field | Generated value | How to read it |
|---|---|---|
| `what_i_checked` | `Whether the matrix equals its transpose (Aᵀ = A).` | The exact question—not a general theory claim. |
| `status` | `verified` | The internal terminal code. |
| `plain_status` | `holds in this check` | The phrase a person should see first. |
| `why` | `Every off-diagonal pair matches its transpose partner.` | The human explanation. |
| `details.mismatches` | `[]` | No mismatching pair was found. A failed receipt lists each location and competing values. |
| `receipt_id` | `sov:sha256:38b2…d07fbd8` | A stable handle for this exact receipt body. Same declared input and check produce the same ID. |
| `next_action` | Use as evidence for this symmetry check only. | The useful decision boundary. |
| `scope` | Exact finite-matrix equality only. | What the receipt deliberately does not establish. |

A failed variant, `[[1, 3], [2, 4]]`, produces `fail` because `[0,1]` is `3` while its transpose partner `[1,0]` is `2`. An incompatible input, such as a non-square matrix, produces `unverifiable`: the system does not guess or silently repair it.

## What advanced users should be able to reveal

| Assurance component | Expose now? | Advanced-user question it answers | Default presentation |
|---|---|---|---|
| Receipt ID and canonical input digest | **Yes** | “Can I replay or reference this exact result?” | Collapsible “Receipt details.” |
| Mismatch/residual evidence | **Yes** | “Why did the check fail?” | Visible when a check fails; expandable when it passes. |
| Fixture/version identifier | **Yes** | “What implementation/test basis produced this?” | “Verification basis” section. |
| Source revision and toolchain | **Yes, exportable** | “Can I reproduce this run?” | Downloadable provenance bundle, not primary UI. |
| Signature / Ed25519 policy | **Later, advanced** | “Who attested to this receipt?” | Disabled until executable vectors and lifecycle policy are complete. |
| Quorum decision and rejected responses | **Later, advanced** | “Did several independent witnesses agree, and what was excluded?” | Advanced audit view; not required for an ordinary local check. |
| Merkle inclusion and consistency proofs | **Later, advanced** | “Can I verify this receipt belongs to an append-only audit history?” | Download/export attachment; do not make it a front-door requirement. |
| Formal anchor references | **Selective** | “What theorem or verified bridge supports this predicate?” | Show only when a genuine bridge exists; never use as decoration. |

### Recommendation

Expose **receipt ID, readable evidence, fixture version, and a downloadable replay bundle** first. Keep signatures, quorum, Merkle proofs, and formal anchors in an **Advanced assurance** drawer. This gives engineers and auditors the evidence they need without forcing ordinary users through terminology that does not help them answer their immediate question.
