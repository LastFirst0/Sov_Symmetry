# Sovereign Engine Full-Program Research and Automation Roadmap

## Goal

Turn Sovereign Engine from a completed **offline universal verification kernel** plus exploratory legacy research code into a disciplined, evidence-first research platform. The platform will support bounded structural checks, reproducible research experiments, trusted data provenance, controlled adapters, reviewable automation, and clear human-facing workflows. It will connect mathematics, software, source data, experimental findings, and lived decision context without presenting any one layer as a substitute for the others.

The operating principle is:

> **An idea may be broad; every executable or communicable claim must be narrow enough to inspect, reproduce, challenge, and revise.**

The roadmap therefore treats the kernel as the **verifier and evidence gate**, not as an autonomous scientific authority. Legacy geometry, language, molecular sequences, AI agents, dashboards, and external data sources become controlled research adapters around that core.

## Starting point and non-negotiable boundaries

| Area | Established status | Roadmap consequence |
|---|---|---|
| Universal kernel | Offline, deterministic core with six structural adapters, empirical-packet boundary, receipts, local assurance, release bundle, and 58 Python / 4 Rust tests in the latest completed release matrix. | Preserve this as the small trusted computing base; do not add network retrieval, autonomous agents, ML inference, or biological interpretation into it. |
| Legacy runtime | Broad geometry-native E8/Hopf/Riemann-Bloch, AI/P2P/runtime ambition; many modules are exploratory or symbolic. | Quarantine as a source of candidate transforms and hypotheses. No legacy label gains verifier authority. |
| Language research pilot | Public Open English WordNet hierarchy pilot was deterministic and negative: the tested Poincaré heuristic did not beat its Euclidean baseline. | Keep the negative artifact as durable evidence; develop the next hypothesis with new public data and a predeclared protocol. |
| Molecular branch | `v2.0-clean-release` contains deterministic codon/amino/protein/genomic prototypes, but core coordinates are currently hash- or hand-authored-feature-derived rather than evidence-based molecular models. | Do not call it validated genomics, protein folding, tissue modeling, longevity modeling, or medical analysis. Use it only as a candidate-transform source after a rewrite and benchmark gate. |
| Dashboard | An interactive evidence dashboard exists and loads a validated ecosystem feed. | Evolve it into the research control surface, but all status data must originate from generated artifacts rather than browser-side interpretation. |
| Personal and experiential context | Important for relevance, intent, impact, and reflection. | Store separately as self-authored context, private by default. It never changes a receipt, review, signature, or scientific status. |

The program explicitly excludes autonomous medical decisions, clinical interpretation, gene therapy or intervention recommendation, handling of personal genomic data, unsupervised release signing, self-admitting adapters, and network-connected behavior inside the trusted kernel.

## Target operating model

The platform will be organized as seven mutually constrained planes. The planes make the project powerful without allowing the most speculative layer to rewrite the most trusted layer.

| Plane | Purpose | Trusted output | Strict boundary |
|---|---|---|---|
| **1. Kernel and evidence plane** | Canonicalize inputs, execute code-owned predicates, hash artifacts, replay receipts, validate release/manifests. | `verified`, `fail`, or `unverifiable` for a declared scope. | Never trains, retrieves, interprets biology, or chooses a theory. |
| **2. Research-proposal plane** | Record hypotheses, sources, candidates, baselines, falsifiers, non-claims, and resource bounds. | Frozen experiment proposal and manifest. | A proposal is not a result. |
| **3. Data-provenance plane** | Retrieve public source data, record source/version/license/query/checksum/splits, and validate packaging. | Dataset manifest and access classification. | No hidden data transformation; no raw restricted data until a separate policy exists. |
| **4. Quarantined runtime plane** | Run geometry candidates, sequence representations, exploratory scripts, and bounded evaluations. | Candidate artifact and reported metrics. | Candidate code cannot sign, approve, alter frozen protocol, or self-promote. |
| **5. Independent evaluation plane** | Recompute baselines/candidates in a pinned environment and emit metrics/uncertainty/logs. | Evaluation bundle. | No access to release keys or mutable evidence. |
| **6. Review and decision plane** | Apply eight gates, validate evidence, collect independent review, and record scope-limited decisions. | Gate receipt and review decision. | No automatic admission to production or theory-level conclusion. |
| **7. Human/product plane** | Show the Reality Trace: situation → claim → evidence → evaluation → review → limitation → next question. | Plain-language, evidence-linked decision support. | Displays context and findings; never masks uncertainty or automates high-impact action. |

## Portfolio workstreams

### Workstream A — Program truth recovery and governance

Create a continuously maintained **research register**. Every work package will name an owner role, repository/source revision, claim class, data classification, expected output schema, risk level, decision gate, expiry/review date, and explicit non-claims. This becomes the authoritative input to the dashboard and automation system.

Implement or consolidate the following governance artifacts before broad automation: a source-manifest format; claim classification taxonomy; evidence-retention policy; data access/license policy; an ADR index; a decision log; a falsification register; a dependency/license register; and a release/change-control policy. A work package without source provenance or an output schema remains `draft`, not “in progress.”

### Workstream B — Kernel, contract, and release hardening

Keep the current offline kernel release as the green core. Complete the signed release-artifact verifier planned in the existing Evidence Operations roadmap: canonical release statement, DSSE envelope, public-key policy, tamper fixtures, CLI verification report, and dashboard status derived from the verifier.

Complete the runtime-neutral adapter lifecycle: code-owned registry, fixture manifest, external starter kit, eight-gate admission report, immutable review events, and a distinct source-code release decision. Add cross-language parity only for explicitly shared fixtures. Expand testing through property tests, mutation/tamper tests, differential tests, clean-install tests, and measured performance tests. No enhancement to the dashboard is considered evidence until it consumes generated verifier output.

### Workstream C — Mathematical and legacy-geometry rehabilitation

Turn legacy mathematical pieces into a queue of **potential bounded adapters**, not a monolithic ontology. Each candidate receives a one-page adapter dossier: object/schema; input canonicalization; exact relation; assumptions; numerical tolerance; reference method; positive/negative/boundary/tamper fixtures; test oracle; non-claims; and falsifier.

Start with one low-risk numerical geometry candidate such as a Möbius-transform identity or Fubini–Study distance property. Do not begin with E8 “meaning,” semantic coherence, Hopf consciousness, or cross-domain claims. A later E8 candidate must operate over a public, source-derived feature vector and defeat matched non-E8 controls; a hash/modulo mapping is not a valid feature transform.

### Workstream D — Reproducible language and molecular research lanes

Maintain independent research lanes with no cross-domain result leakage:

| Lane | First bounded question | Required public data | Success condition | Explicit non-claim |
|---|---|---|---|---|
| **L1: Lexical structure** | Can a declared representation improve relation recovery? | Open English WordNet or a second pinned lexical benchmark. | Beats Euclidean/random controls on held-out relation recovery and replicates. | Not a discovery of universal language geometry. |
| **M0: DNA sequence geometry** | Can a hyperbolic representation beat matched Euclidean controls on a named public regulatory/promoter classification task? | One license-reviewed GUE task with frozen split/checksum, public A/C/G/T sequences only. | Predeclared test metric, paired bootstrap advantage over both controls, three seeds, independent replication. | Not a gene-function, disease, aging, or intervention conclusion. |
| **P0: Protein representation** | Can a declared representation predict a bounded public structural/function label? | PDB/CATH/ProteinWorkshop-style task with documented splits. | Beats matched controls; explicit structure/sequence leakage audit. | Not protein folding, drug discovery, or therapeutic inference. |
| **X0: Cross-scale relation** | Can two already validated representations be linked by a typed, declared relation? | Prior lane artifacts only. | A precise relation/fixture passes or fails reproducibly. | Not holography, universal correspondence, or causal unification. |

M0 is the recommended next experiment. It will replace the `v2.0-clean-release` branch’s manually curated species table, hash-derived coordinates, and symbolic codon mapping with raw public sequences, source metadata, matched baselines, split discipline, independent evaluation, and an explicit negative-result path.

### Workstream E — Data and research-source control plane

Build a source adapter pattern that every public data acquisition follows:

```text
retrieval request → source response → raw file locator → license/access check
→ canonical dataset manifest → checksum → split/transform manifest
→ validation report → frozen experiment input
```

Every source manifest must record provider, API/query parameters, retrieval time, stable identifiers, release/version, license/access status, raw/processed checksums, transformation version, input schema, and known limits. Refreshing a source never overwrites a frozen data package; it creates a new version and triggers a change-impact review.

| Source family | Approved initial role | Integration policy | Not in scope without a new approval |
|---|---|---|---|
| NCBI Entrez / E-utilities | Public references and non-clinical sequence metadata retrieval. | Rate-limited deterministic retrieval; query/source manifest; public data only. | Personal genomics, patient records, clinical decision support. |
| UniProt REST | Protein sequence and curated functional metadata for P0. | Pin accession/release, license, field selection, and raw result digest. | Inferred biological mechanism or intervention recommendation. |
| RCSB PDB Data/Search APIs | Public structure metadata and benchmark assembly. | Pin PDB IDs, mmCIF/data schema version, query and structure release. | Clinical structural interpretation. |
| ENA/EBI / GUE source releases | Public sequence benchmark acquisition. | License and split review before use; immutable raw artifact copy. | Live, unversioned sample streaming. |
| PubMed/PMC/Crossref/OpenAlex | Literature intake and citation graph. | Metadata-only index; primary sources linked and reviewed; agent summaries are drafts. | Literature-derived `verified` status. |
| Zenodo/DataCite | Dataset/artifact discovery and DOI provenance. | Record DOI/version/checksum/access terms. | Automatic import of executable artifacts. |

The currently available platform integrations should be explicitly classified: **GitHub** is development/provenance only; **Cloudflare** is optional hosting/deployment only; **Mobbin** is UI-reference research only; financial, crypto, and public-health feeds are excluded from the core program unless a future approved work package needs them. No connector is enabled merely because it is available.

### Workstream F — Feedback-loop and orchestration control plane

Implement the `Legacy Runtime ↔ Universal Kernel Feedback Loop Specification v0.1` in stages. Its non-negotiable order is:

```text
human-authored proposal → frozen protocol → quarantined candidate
→ independent evaluation → kernel gate receipt → human review
→ bounded feedback packet → next candidate or closure
```

The first implementation remains local and offline after input retrieval. The runtime can receive only protocol-approved aggregate feedback, reason codes, and permitted next actions. It never receives private review keys, release-key access, mutable evidence-write access, or the ability to change its own success metric.

For optional task orchestration, use the Manus API v2 as a **draft/research assistance control plane** only. A structured work-package result must include source manifest, task profile, output schema, confidence/limitation, artifacts, and terminal state. Webhook callbacks require signature verification, idempotency keys, retry limits, and dead-letter handling. Neither an agent response nor an external connector result is a kernel verdict until a deterministic gate validates its packaged evidence.

### Workstream G — Dashboard, documentation, and human experience

Evolve the dashboard into a read-only first **Research Mission Control** surface backed by generated manifests. Priority components are: Research Register; Reality Trace / Claim Composer; dataset and experiment catalog; candidate-versus-baseline comparisons; evidence and uncertainty explorer; adapter review queue; signed release root-of-trust view; assumption/change-impact graph; evidence-gap board; and private Experience & Meaning Lane.

Each research result page must show five plain-language sentences: **what was asked; what was used; what happened; what this does not establish; and what responsible next question follows.** The molecular lane must use a distinct non-clinical warning and never show therapeutic or personal health language.

Create a single documentation home that distinguishes: public orientation, developer contracts, adapter authorship, research protocols, data source catalog, automation runbooks, evidence/release guide, legacy archive, and results registry. All examples use actual fixture names or generated artifacts; none use vague claims of coherence, emergence, or intelligence without declared definitions and evidence class.

### Workstream H — Skills and reusable capabilities

Do not bulk-install skills. Each external skill is untrusted until its repository, license, maintenance state, resource requirements, data practices, and overlap with existing skills are reviewed. The plan therefore uses a **discover → inspect → trial in quarantine → score → approve → import** workflow. Import occurs only after a scorecard and a reversible rollback path are recorded.

| Capability | Current reusable capability | Candidate to evaluate before import | Approval test |
|---|---|---|---|
| Evidence strategy / release gates | Existing evidence-first strategy skill | None required initially. | Reuse existing policy; compare only if a credible specialized alternative emerges. |
| OSS solution discovery | Existing GitHub solution research skill | Scientific-agent repository patterns only. | License, maintainer activity, deterministic behavior, no hidden data exfiltration. |
| Scientific/bioinformatics research | No approved molecular workflow skill yet. | K-Dense scientific-agent skills: evaluate individual sequence-data, protein-structure, literature, and reproducibility modules—not the repository wholesale. | Each selected module must work on public data, expose sources, and fit evidence packaging. |
| Experiment reproducibility | Existing evidence/fixture processes. | Candidate ML experiment tracking/reproducibility skill. | Must preserve seeds, hashes, environment, baselines, and failure artifacts. |
| Data provenance | Existing documentation/manifest tools. | Candidate FAIR/metadata/data-catalog skill. | Must produce versioned source manifests and never infer missing license/provenance. |
| Scientific literature synthesis | Existing research tools plus source policy. | Candidate literature-review skill. | Requires citations, primary-source links, uncertainty, and no “verified” language. |
| Automation policy | Existing automation and persistent-computing guidance. | No new skill before a runbook is stable. | Typed inputs/outputs, least privilege, bounded retry, disable/rollback procedure. |

Create custom Sovereign skills only after three successful uses of the same stable workflow. The planned candidates are: `sov-research-work-package`, `sov-dataset-manifest`, `sov-molecular-benchmark`, `sov-experiment-gate`, `sov-adapter-review`, `sov-release-evidence`, and `sov-dashboard-feed`. Each custom skill will package only the non-obvious policy, schemas, templates, and deterministic scripts needed for repeatability. It will be initialized, tested, and validated separately; no custom skill will encode unverified theory as a rule.

### Workstream I — Automation and operating architecture

Automation will be introduced in tiers, after the source-manifest and work-package schemas are accepted. It will not mean “run everything continuously.” It will mean **run the right bounded checks at the lowest safe frequency, record the result, and stop on uncertainty**.

| Option | User experience | Best use | Tradeoffs | Initial recommendation |
|---|---|---|---|---|
| **Managed research console with scheduled jobs** | A dashboard provides run controls, catalogs, status, and periodic refreshes without the user keeping a machine open. | Daily/weekly deterministic source refresh, manifest validation, GitHub evidence scan, and dashboard feed regeneration. | Best for light jobs; task-specific scientific libraries or long experiments may exceed managed limits. | Start here for program control and metadata refresh. |
| **Dedicated persistent research worker** | A continuously available isolated worker runs heavier reproducible experiment containers and stores frozen datasets/artifacts. | Specialized Python/R/Bioinformatics dependencies, long-running benchmark jobs, larger datasets, or strict environment pinning. | Requires a separately governed deployment, OS/dependency hardening, monitoring, storage, and operational budget. | Add only when M0 or P0 demonstrates a concrete runtime/resource requirement. |
| **On-demand research packet execution** | A human starts a bounded task with a frozen proposal; results return to the registry. | Hypothesis design, literature review, major experiment launches, review summaries. | Adds latency and requires explicit authorization; not suitable for high-frequency polling. | Use for judgment-heavy work only. |

Initial automation inventory:

| Job | Trigger/frequency | Deterministic behavior | Terminal behavior on failure |
|---|---|---|---|
| Repository evidence scan | Push/webhook or daily fallback after webhook verification. | Capture commit, changed manifests/contracts, CI state, dependency diff. | `unverifiable` event; no release/readiness change. |
| Dataset drift scan | Weekly, never high-frequency. | Compare provider/version/checksum to frozen source registry. | Create a new-source obligation; never replace frozen input. |
| Release evidence validation | On explicit release-candidate build. | Run full matrix, manifest/tamper checks, checksum and verifier report. | Block release. |
| Experiment gate | Explicit human-approved start. | Validate proposal, run bounded evaluator, create bundle, evaluate predicates. | Preserve logs/artifacts; mark `fail` or `unverifiable`; no automatic retry mutation. |
| Literature intake | Weekly metadata collection plus human triage. | Retrieve metadata/source URLs, de-duplicate, classify into research register. | Retain source error; no unsupported summary. |
| Dashboard feed refresh | Only after a validated artifact changes. | Regenerate read-only feed from manifests. | Keep last known valid feed; show stale/unavailable state. |
| Skill/dependency watch | Monthly. | Check approved repositories/releases/licenses against recorded allowlist. | Create review ticket; never auto-upgrade or auto-import. |

Every automation has a runbook covering owner, inputs, limits, credentials, idempotency key, retry budget, time limit, expected outputs, log/receipt location, alert target, and immediate disable switch. Event-driven webhooks will be adopted only after confirming the provider’s current webhook support and signature process from official documentation. High-frequency polling is prohibited.

### Workstream J — Ecosystem, audience, and keyword research

Run ecosystem comparisons in five categories: verification/evidence systems, reproducible scientific workflow tools, symbolic/numeric mathematics, molecular ML/research benchmarks, and agent/orchestration platforms. Score candidates for semantics, deterministic fit, offline capability, licensing, maintenance, integration burden, data safety, and abandonment risk.

Build a persona and terminology map for researchers, scientific software engineers, AI systems builders, technical educators, reviewers, and developer integrators. Translate internal vocabulary such as “kernel,” “receipt,” “adapter,” and “unverifiable” into tangible outcomes: proving a data handoff, reproducing a benchmark, checking a constraint, reviewing a claim, or documenting a failed candidate.

The quantitative keyword research workstream remains deliberately blocked until the project records: target country or worldwide scope, target domain/site, audience priority, seed topics, and source of volume/competitor data. Once supplied, use the mandated three-tab/300-keyword process; until then, provide qualitative terminology and content-gap research only and do not fabricate volume, CPC, traffic, or difficulty.

## 30/60/90-day execution sequence

| Horizon | Primary outcomes | Acceptance evidence |
|---|---|---|
| **Days 0–15: establish control** | Freeze research register and source manifest; audit repository/branch/connector capabilities; adopt the data-source and experiment schemas; complete signed-release verifier design; score external skills and OSS candidates without importing them. | Every work package has source/input/output/non-claim; connector/skill/dependency registers exist; no unapproved external integration is active. |
| **Days 16–30: make M0 runnable** | Acquire and license-review one public GUE DNA task; build data validator/manifests; implement random and matched Euclidean baselines; define hyperbolic candidate contract; add experiment-gate fixtures; build first Research Mission Control data model. | Frozen dataset/split artifact; reproducible baseline run; malformed/leakage/tamper data cases fail; dashboard displays generated research records. |
| **Days 31–45: run and audit M0** | Execute M0 under resource bounds; publish candidate/baseline/uncertainty artifacts; run independent rerun; retain negative result if applicable; review legacy E8 candidate dossier without executing it. | Evaluation bundle, gate receipt, review decision, source manifest, environment record, and plain-language limitations report. |
| **Days 46–60: extend platform integrity** | Implement adapter review workflow and signed release view; turn stable dataset/experiment workflow into one or two custom skills; add dependency/skill watch and source drift jobs. | Transition/tamper/role tests pass; dashboard is fail-closed; custom skills pass validation; automated runs create append-only records. |
| **Days 61–75: replication and protein planning** | Replicate M0 on a second task; decide whether evidence supports P0; assemble P0 public structure/sequence protocol; run documentation/UX comprehension studies. | Replication report or explicit non-replication result; P0 proposal/falsifier/manifest ready; comprehension results and content-gap recommendations recorded. |
| **Days 76–90: release a research-platform milestone** | Package a versioned research protocol kit, updated dashboard, validated skill set, signed release evidence, and execution portfolio for the next quarter. | Full release matrix; evidence/skill/source manifests; open-risk register; published non-goals; decision log contains only consequential unresolved items. |

## Cross-cutting test and falsification policy

Every research or operational capability must have one or more of these gates: schema validation, exact fixture, malformed input, one-field tamper case, deterministic replay, split-leakage audit, baseline comparison, uncertainty calculation, independent rerun, access/license validation, role/transition check, and user-comprehension test.

The claim-promotion ladder is fixed: `logged → specified → data-pinned → fixture-tested → independently evaluated → reviewed experimental result`. No stage implies the next. A result can be useful while remaining negative, incomplete, or `unverifiable`.

## Roles, decision rights, and escalation

| Role | Default authority | Escalate when |
|---|---|---|
| Kernel/release steward | Core contracts, evidence predicates, release gate, key policy. | A change alters terminal status semantics or security boundary. |
| Research protocol steward | Proposal schema, data source/split, metric, baseline, falsifier, non-claims. | A study enters clinical/personal genomic data or changes a frozen protocol. |
| Data steward | License/access/provenance, retention, data versioning, retrieval policy. | Source data is restricted, unclear, personal, or potentially sensitive. |
| Runtime/evaluation steward | Quarantined candidate environment, reproducible evaluator, resource policy. | Workload needs privileged runtime, persistent compute, or new dependencies. |
| Review authority | Evidence completeness and scoped admission/rejection. | A result is proposed for external publication, high-impact decision use, or adapter release. |
| Product/experience steward | Dashboard, documentation, terminology, accessibility, comprehension. | A UI could make a personal interpretation appear verified or a research result look medical. |

## Key risks and mitigations

| Risk | Trigger | Preventive control | Failure response |
|---|---|---|---|
| Theory contamination of the kernel | Framework label starts selecting code/tolerance/status. | Code-owned registry, neutrality tests, eight-gate review. | Quarantine adapter; produce theory-leakage report. |
| Molecular overclaim | Prototype output is framed as genomics, folding, longevity, or therapy. | Non-clinical policy, public data only, benchmark labels, visible non-claims. | Block publication/promotion; correct labels and evidence record. |
| Data leakage | Duplicate/homologous/near-identical sequences cross splits. | Split/duplicate/reverse-complement/homology audit before run. | Mark evaluation `unverifiable`; rebuild split and rerun. |
| Automation overreach | A worker retries, upgrades, approves, or changes protocol autonomously. | Typed work packages, explicit transitions, minimal privileges, kill switch. | Disable job; preserve incident manifest; require human reauthorization. |
| External dependency drift | Source/API/model/skill changes silently. | Pin versions/digests; source/skill watch; lockfile and manifest policy. | Create new version obligation; keep previous valid artifact. |
| Secret/connector sprawl | Broad credential used by unnecessary job. | Least-privilege matrix, short-lived/revocable credentials, no secrets in evidence. | Disable connector; rotate credential; audit affected runs. |
| Communication gap | Users cannot tell check, interpretation, and uncertainty apart. | Reality Trace, non-claim cards, guided tests, terminology map. | Revise UX/docs and retest comprehension. |

## Assumptions and constrained open decisions

The roadmap assumes GitHub access remains available for source/release evidence and public data APIs may be used only after their licenses/rate limits are recorded. The current MCP list does not provide a biology data service, so biology retrieval begins through official public APIs or a user-approved connector; no custom connector is created in planning.

Three decisions are intentionally left for approval before production-facing execution: the project’s target market/country and SEO data provider for quantitative keyword research; the long-term hosting route if M0/P0 needs more than a managed dashboard’s periodic-job capacity; and any external data credentials beyond public endpoints. None blocks immediate schema, protocol, dashboard-data-model, or skill-evaluation work.

## Completion standard

The program is ready to “run on all cylinders” only when automation is not merely busy: all active pipelines have a source manifest, frozen input, explicit ownership, bounded capability, deterministic or reviewable output, terminal status, replay/tamper behavior, dashboard projection, disable path, and documented limitation. At that point, multiple research lanes can progress in parallel without allowing a result from one domain, a speculative legacy transform, or an agent-generated summary to outrun the evidence that supports it.
